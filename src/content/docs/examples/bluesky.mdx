This page is a real teardown, not an illustration. The handbook's probes were run on the Bluesky app, the outcomes were recorded in the worksheet, and every conclusion was then checked against the app's source code, which its maker publishes.

It exists to answer one question: does reading an app from the outside give you the right design?

:::note[Why a real app is named here]
The handbook's chapters describe generic app types and name no products. This page is the one exception. Everything in the first half is an observation of behavior, marked with a confidence word. Everything in the second half is taken from source code that Bluesky's maker has published.
:::

Twenty probes is a small sample, and one teardown of one app does not prove the method for all apps. It shows that the method produced no wrong conclusion here, and it shows where the probes were too weak to decide.

The [second worked example, Expensify](/examples/expensify/), is the harder test. There the method was wrong three times, and the page shows each one.

### Launch and startup ([Chapter 7](/part-2-concerns/7-launch-and-startup/))

| Probe | What was seen | Reading | Confidence |
|---|---|---|---|
| P7.1 Cold against warm | Three cold starts drew a first frame after 1.1, 3.0 and 2.9 seconds. A return to the running app took 0.6 seconds. | A real cold start with visible work, and a resume that does none | Observed |
| P7.2 First-screen strategy | Splash, a blank frame, the home layout with gray placeholder rows, then posts | Skeleton placeholders. The first frame does not wait for content | Observed |
| P7.3 Launch in airplane mode | Opened signed in, with the home layout and placeholders. No posts, no error and no offline message in 30 seconds | The session check is local. Content is not stored across launches | Inferred |
| P7.4 Where it lands | Home after a force-quit from another tab, and Home after the process was ended from a post thread | The app always lands on Home and does not save the last screen | Inferred |

| Probe | What was seen | Reading | Confidence |
|---|---|---|---|
| P8.1 Tab histories | A tab switch, an opened post and 20 seconds in the background each returned to the same posts at the same pixel positions | Each tab has its own stack, kept alive while another tab shows | Inferred |

| P8.5 Link while signed in | A link to a profile, opened with the app closed, cold-started the app on that profile | A router maps the link to a screen from a cold start | Observed |

| P8.7 Link into a running app | The profile opened over the feed, and back returned to the feed | The target is presented over the current place | Observed |

### Data, caching and offline (Chapters [9](/part-2-concerns/9-state-and-ui-data-flow/), [11](/part-2-concerns/11-local-storage-caching-and-prefetching/), [12](/part-2-concerns/12-offline-and-sync/), [13](/part-2-concerns/13-network-transport-and-resilience/))

| Probe | What was seen | Reading | Confidence |
|---|---|---|---|
| P11.1 Memory or disk | Offline, the feed and an opened thread stayed visible while the app was alive. After a force-quit they were gone | The data cache is in memory only | Inferred |
| P12.1 Offline read | Visited screens kept their content offline. Tabs never opened showed placeholders | Offline Level 1 within one run of the app, Level 0 across launches | Inferred |
| P11.6 Unvisited detail | Offline, a post never opened showed its thread header at once, with image, exact time and counts | The detail screen is seeded from data the feed row already carried | Inferred |
| P9.5 Failed refresh | Offline, a pull to refresh left the posts in place. No error or banner was seen 2, 8 and 22 seconds later | The content stays and nothing reports the failure | Inferred |
| P13.2 Recovery | With the feed stuck on placeholders, the network was restored and the app was not touched. Posts appeared 6 to 12 seconds later | The app watches the network and resumes waiting requests by itself | Inferred |
| P4.1 Footprint | User data went from 6.3 MB to 7.2 MB in 20 minutes of browsing. The cache figure went from 10.2 MB to 29.5 MB | A cache filled by visits, held in the area the system counts as cache | Inferred |
| P11.5 Clear cache | The app's own Clear image cache control dropped the cache from 29.5 MB to 7.2 MB. User data and the session were untouched | The control clears a disk cache of images and nothing else | Inferred |

Put together, these seven probes give a precise picture: **posts live in memory and are refetched on every launch, while images are cached on disk**. That is why the storage figure grows although the feed is gone after a force-quit.

## The design, as read from outside

Before the source was opened, the worksheet said this:

- **Startup.** A local session lets the app draw its home layout at once. Content is fetched after the first frame, behind placeholders. Nothing about the last screen is saved.
- **Data.** One in-memory cache serves every screen, and a detail screen starts from the row that led to it. The cache dies with the process. Only a little state survives a launch: the session, the list of feeds, and preferences.
- **Images.** A separate disk cache, which the user can clear.
- **Offline.** No offline mode and no offline message. Requests wait, and resume when the network returns.
- **Navigation.** A tab bar with one stack per tab. Links are routed to a screen with a Home screen placed under it.
- **Backend implied.** A read API that returns feed rows complete enough to draw a thread header, and a feed service that ranks on every request.

## Checked against the source

| Conclusion | Verdict | What the source shows |
|---|---|---|
| Placeholders on the first screen (P7.2) | <span class="verdict verdict-confirmed">Confirmed</span> | The feed renders a `PostFeedLoadingPlaceholder` component while loading |
| Feed data is in memory only (P11.1, P12.1, P7.3) | <span class="verdict verdict-confirmed">Confirmed</span> | `src/lib/react-query.tsx` saves a query to disk only when its key carries a `persistedVersion`. The post feed's key does not. The keys that do are feed information, preferences, labeler details, join links and chat status, which matches the feed tabs and interests that were visible offline |
| No saved navigation state (P7.4, P8.3) | <span class="verdict verdict-confirmed">Confirmed</span> | The navigation container in `src/Navigation.tsx` is given no initial state and saves none. This settles the Speculative reading of P8.3: memory only, not a time limit |
| One stack per tab (P8.1) | <span class="verdict verdict-confirmed">Confirmed</span> | A bottom tab navigator holds a separate stack navigator for Home, Search, Notifications, Messages and Profile |
| Links open the item (P8.5) | <span class="verdict verdict-confirmed">Confirmed</span> | The linking configuration lists `https://bsky.app` among its prefixes |
| Synthesized back stack (P8.6) | <span class="verdict verdict-confirmed">Confirmed</span> | `getStateFromPath` builds the state with a Home route under the target. Its comment says the Home tab must be initialized "otherwise the back button will not work" |
| Detail seeded from the list (P11.6) | <span class="verdict verdict-confirmed">Confirmed</span> | The thread query searches the feed, notification, search and other caches for the post and uses it while the thread loads |
| Recovery without user action (P13.2) | <span class="verdict verdict-confirmed">Confirmed</span> | The app listens for network changes, checks every two seconds while it believes it is offline, and tells the query library when the network is back |
| The control clears images only (P11.5) | <span class="verdict verdict-confirmed">Confirmed</span> | The About settings screen calls the image library's `clearDiskCache` |
| Text is not selectable in the feed (P32.1) | <span class="verdict verdict-confirmed">Confirmed</span> | Only the main post of a thread and translated text are marked selectable. The probe did not try the thread screen, where it would have found selection |
| Nothing reports a failed refresh offline (P9.5) | <span class="verdict verdict-consistent">Consistent</span> | The query library pauses requests while offline instead of failing them, and no offline message was found in the feed component. The refresh path was not traced end to end |
| Link into a running app (P8.7) | <span class="verdict verdict-consistent">Consistent</span> | The behavior comes from the navigation library the app uses. The app adds nothing that contradicts it |
| Storage growth is image cache (P4.1) | <span class="verdict verdict-consistent">Consistent</span> | The image library keeps a disk cache, and clearing it removed the growth. Other contributors, such as video, were not ruled out |
| Text follows the system size (P32.2) | <span class="verdict verdict-consistent">Consistent</span> | Several components set a maximum text scale. The cap on the measured label was not traced |
| No licenses screen (P38.1) | <span class="verdict verdict-consistent">Consistent</span> | No licenses screen was found in the settings source. Absence is hard to prove |
| Fresh ranking on each refresh (P15.5) | <span class="verdict verdict-unknown">Not in the client</span> | The Discover feed is produced by a backend feed generator. The client only asks for it |
| Cold start timing (P7.1) | <span class="verdict verdict-unknown">Not in the client</span> | A measurement, not a design decision in the code |

## What the method missed

An honest account of where reading from outside fell short in this run.

- **The technology.** The source shows a cross-platform app built on a mapped toolkit ([Chapter 32](/part-2-concerns/32-ui-technology-native-cross-platform-and-web/)). The probes that would suggest this, a screen reader walk and a comparison across two platforms, were not run. Nothing in the 20 probes pointed to it.
- **One probe could not be run at all.** P15.1 needs a fast fling. Scroll commands sent to an emulator are too slow to count as one, so it was left unrecorded instead of guessed.
- **One probe was too weak.** P11.6 was run on a post with no replies, so a failed fetch of replies would have been invisible. The conclusion happened to be right. On a post with replies it would have been earned.
- **One probe stopped too early.** P32.1 tested the feed and a tab label. The thread screen, where text can be selected, was not tried.
- **Absence is weak evidence.** "No error was seen" (P9.5) and "no licenses screen" (P38.1) are the least certain entries, as [Chapter 5](/part-1-method/5-from-signal-to-inference/) says they must be.
- **What needs a second device or real time was skipped.** Real-time delivery, sync between devices, long absences and anything that writes were out of scope for a read-only run on one emulator.

## Run it yourself

The recorded teardown is in the repository under `teardowns/bluesky/`, with the generated report and the screenshots.

- **By hand:** install any app on a phone or an emulator, open [Chapter 4](/part-1-method/4-probes/), and record what you see in the [worksheet](/worksheet/).
- **With an AI coding agent:** from the repository, one command hands the playbook to your agent, which runs the probes that one emulator allows and writes the report.

```bash
npm run teardown -- xyz.blueskyweb.app
```

Replace the app id with any app installed on your running emulator or simulator.
