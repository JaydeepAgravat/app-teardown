This is the second real teardown, run the same way as the [Bluesky example](/examples/bluesky/): probes on an emulator, outcomes recorded in the worksheet, and every conclusion then checked against source code the app's maker publishes.

Expensify was chosen because it is the opposite of Bluesky in the way that matters most to this handbook. Bluesky keeps its data in memory. Expensify is built to work offline. If the probes can tell the two apart, they are measuring something real.

They did tell them apart. They also produced three wrong readings, which are listed in full here and have been corrected in the chapters.

:::note[Why a real app is named here]
The chapters name no products. The worked examples are the exception. What was seen carries a confidence word. What is said about the app's internals comes from source code and design notes its maker has published.
:::

### Offline and sync ([Chapter 12](/part-2-concerns/12-offline-and-sync/))

This is the chapter Expensify exercises best, and the probes ran in sequence on one test message.

| Probe | What was seen | Reading | Confidence |
|---|---|---|---|
| P12.1 Offline read | After an offline cold start, the Inbox listed its chats with previews, and a chat opened with its history from 2025. Neither had been opened in that run | A local replica, filled ahead of need | Inferred |
| P12.2 Offline write | A test message sent offline appeared at once, drawn dimmed | An optimistic update with a tracked mutation | Observed |
| P12.3 Kill while pending | Force-quit and offline relaunch. The message was still there, still dimmed, and was the preview on the chat's Inbox row | The outbox and the local change are stored durably | Inferred |
| P12.4 Reconnect | With the chat closed and the app on its Home tab, the network came back for 25 seconds. Reopened offline, the message was at full brightness and its time had moved from 9:41 to 9:42 PM | A sync engine at app level drains the outbox | Inferred |

Two further things were seen that match signals in the chapter's table, though no probe asks for them:

- **The time shift.** The message's time changed by a minute once it was confirmed. That is the "item order or timestamp shifts slightly after sending" signal: confirmed backend values replacing local ones.
- **The pending delete.** A second test message deleted offline was struck through and dimmed, and vanished when the network returned. Pending adds and pending deletes are drawn differently.

## Checked against the source

| Conclusion | Verdict | What the source shows |
|---|---|---|
| Offline writes are optimistic and drawn dimmed (P12.2, P4.2, P3.1) | <span class="verdict verdict-confirmed">Confirmed</span> | The maker's own offline design notes describe queuing a request and proceeding "as if the request succeeded". A wrapper component dims its content while offline with a pending action |
| The outbox is durable (P12.3) | <span class="verdict verdict-confirmed">Confirmed</span> | Queued requests are kept in the app's persistent store under a key named `networkRequestQueue` |
| An app-level sync engine drains it (P12.4, P13.2) | <span class="verdict verdict-confirmed">Confirmed</span> | A sequential queue in the network layer subscribes to network state and flushes when the device is back online. It belongs to no screen |
| Content is stored on the device (P7.3, P11.1, P12.1) | <span class="verdict verdict-confirmed">Confirmed</span> | The app keeps its data in a persistent store that every screen reads |
| Drafts are stored as data (P8.2, P8.4, P4.3) | <span class="verdict verdict-confirmed">Confirmed</span> | The store has a collection keyed by chat for draft comments |
| Synthesized back stack for links (P8.6) | <span class="verdict verdict-confirmed">Confirmed</span> | The link handler computes a matching full-screen route to place under the target, for back to lead to |
| Text does not follow the system size (P32.2) | <span class="verdict verdict-confirmed">Confirmed</span> | The app's text component turns font scaling off |
| Pending deletes are struck through | <span class="verdict verdict-confirmed">Confirmed</span> | The same wrapper applies a strikethrough when the pending action is a delete. Not counted in the score, since no probe asked for it |
| Links open the page (P8.5), replace the current place (P8.7) | <span class="verdict verdict-consistent">Consistent</span> | The link configuration and the adapted-state helper exist and match the behavior. The path was not traced end to end |
| Detail on device before open (P11.6), one copy for list and detail (P9.1), growth in user data (P4.1) | <span class="verdict verdict-consistent">Consistent</span> | All three follow from one persistent store that screens subscribe to. Not traced for these specific screens |
| No text selection, own action list (P32.1) | <span class="verdict verdict-consistent">Consistent</span> | A context menu component provides the copy actions |
| Cold start timing (P7.1) | <span class="verdict verdict-unknown">Not in the client</span> | A measurement |
| **A blocking fetch behind the splash (P7.2)** | <span class="verdict verdict-wrong">Contradicted</span> | The splash is hidden when navigation is ready and the language is loaded. Both are local. Probe P7.3 had already shown the same thing: the splash ended in content with no network |
| **The app does not persist the last screen (P7.4)** | <span class="verdict verdict-wrong">Contradicted</span> | The app saves the last visited path to its store on every navigation, and has startup code that restores it. That code returns early for an account on a public email domain. The test account uses a consumer email address, which would explain what was seen, though the flag was not checked on the account itself. The behavior seen was real. The design claim drawn from it was wrong |
| **Memory only, or a time limit (P8.3)** | <span class="verdict verdict-wrong">Contradicted</span> | Same cause. The reading offered two candidate designs and the true one was neither |

## The three wrong readings, and what changed

Each failure had the same shape: the behavior was recorded correctly, and the probe's reading claimed more than the behavior supports.

**1. P7.2 read a splash as a network wait.** Its first outcome said "a blocking fetch behind a splash". A splash can equally cover local work, such as opening a stored database. The probe that separates the two, launching in airplane mode, was the very next one, and it gave the right answer. The reading now names both candidates, points to P7.3 to separate them, and is marked Speculative.

**2. P7.4 turned "it landed on Home" into "it does not save the last screen".** Expensify does save it, and restores it for some accounts. From one account, a condition on account type is invisible. The reading now says what was seen and lists conditional restoration as a candidate.

**3. P8.3 listed two candidates and missed the third.** It now includes conditional restoration and says plainly that one account on one device cannot rule it out.

This is the rule from [Chapter 5](/part-1-method/5-from-signal-to-inference/) applied to the handbook itself: list every candidate design before choosing. All three corrections are in the chapter data, so the next teardown, by a person or an agent, gets the corrected readings.

## What else the method missed

- **The technology.** As with Bluesky, the source shows a cross-platform app, and no probe that was run pointed to it.
- **One probe did not apply.** P8.1 compares tab histories, but this app hides its tab bar on every pushed screen, so there is no way to switch tabs from inside one.
- **A source newer than the app.** The code checked is one version line ahead of the build tested. A behavior could differ between them for that reason alone.
- **What needs a second device was skipped.** Conflicts between two devices, real-time delivery to another person, and anything involving a second account.
